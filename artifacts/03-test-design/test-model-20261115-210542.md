## 3. Конвенции проектирования

1. **Типы кейсов.** `positive` / `negative` / `boundary`; тема `[TC] <название> (<тип>)`. В этом прогоне не применимы: нет ни одного публикуемого требования.
2. **Трассировка.** `requirement_id` — временные ID аудитора (R-01, R-02; GAP-007: у источника собственной нумерации нет).
3. **Rule «нет кейсов без expected_result».** Соблюдена формально: исполняемых кейсов 0 → нарушений 0. Заглушки кейсами не являются.
4. **Boundary policy.** В #116 числовые ограничения отсутствуют (нет лимитов длины, числа попыток, таймаутов) → `BOUNDARY_NOT_APPLICABLE`; выдумывать границы запрещено. Дополнительно вся зона заблокирована.
5. **Приоритет заглушек.** Правило: приоритет = severity ведущей блокирующей проблемы (`Critical→#3`, `Major→#2`, `Minor→#1`). R-01/R-02 ведут Blocking-проблемы GAP-001/GAP-002 (Critical) → `Critical`; flow/ошибки/предусловия/SEC-01 ведут Major → `Major`.
6. **Трекер заглушек.** `Task (#2)`, а не `TestCase`: заглушка не является исполняемым кейсом, её presence в `TestCase` сломала бы фильтр «исполняемые кейсы» и правило «нет кейсов без expected_result». Исполняемые кейсы (в будущем) — `TestCase (#1)`.
7. **Иерархия.** `parent_issue_id` намеренно не задан: структура связей #116 не проверялась (директива), а связывание было бы изменением топологии без запроса. Ссылка на источник — текстом `related_requirement_issue: #116`.
8. **Предусловия.** Формальные отсутствуют (GAP-006, PRECOND_DERIVED) → в заглушках не используются как факт; производные заготовки не подтверждаются (зависят от OQ-2).
