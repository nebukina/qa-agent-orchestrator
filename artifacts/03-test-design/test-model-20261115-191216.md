## 3. Конвенции проектирования

1. **Типы кейсов.** `positive` — штатный сценарий соблюдения требования; `negative` — невалидные/нештатные входные данные либо невыполненное предусловие. Тема: `[TC] <название> (<тип>)`.
2. **Pending-OQ policy.** Для PROBLEMATIC-требований в `expected_result` входят только детерминированные ассерты. Спорные ассерты вынесены в блок «Вне зоны верификации (pending OQ)» и **не участвуют в вердикте** «прошло/не прошло». Значения (цвет, место появления, нормативный критерий email, моделирование «недоступен») **не выдумываются**.
3. **Boundary policy.** В требованиях #120 числовые ограничения отсутствуют (нет лимитов длины полей, количества попыток, таймаутов). Boundary-кейсы не создаются: **BOUNDARY_NOT_APPLICABLE** (см. Gaps). Выдумывать границы запрещено директивой.
4. **GAP-заглушки.** Для BLOCKED RQ создаются issues с префиксом `[GAP]` и маркером `BLOCKED_BY_OPEN_QUESTION`, **без шагов и без expected_result** (иначе пришлось бы выдумывать AC).
5. **Тестовые данные.** Синтетические фикстуры: `EMAIL_VALID_FIXTURE = tc.rq120.user@example.test` (валидно при обеих трактовках OQ-01), `PASSWORD_FIXTURE = <имя фикстуры тестовой среды, значение не публикуется>`. Реальные пароли/токены в артефакт и в Redmine не попадают.
6. **Предусловия** выведены из отчёта (секция PRECOND_DERIVED): пользователь на странице авторизации; активной сессии нет; `/api/login` доступен (кроме негативных сценариев).
7. **Мок-ответы.** Для RQ-09/RQ-11 используется перехват (mock) `/api/login`, возвращающий ровно HTTP 200 / ровно HTTP 500. Сетевая недоступность (timeout/offline/DNS) не моделируется — pending OQ-02.

- **Не покрыто сознательно (вне объёма существующих RQ, ждут OQ):** прочие HTTP-коды и сетевые сбои (OQ-06), механизм сессии (OQ-07), anti-double-submit (OQ-08), жизненный цикл сообщения (OQ-09), стиль сообщения 500 (OQ-10), NFR (OQ-11), локализация (OQ-12).

Диагноз: отказ **системный и авторизационный**, а не валидационный. Инструмент `create_issue` валидирует tracker/priority ДО записи и при некорректных параметрах вернул бы другое сообщение; здесь отклонение произошло на уровне права выполнения действия. Тот же отказ на `kind=me` при работающих read-вызовах подтверждает отсутствие права записи у учётной записи MCP.

Дальнейшие вызовы `create_issue` для остальных 14 единиц **не выполнялись**: по Failure Behaviour скилла ошибка авторизации при создании кейсов означает «лог, остановка, эскалация», а директива ограничивает число попыток 2 на единицу. Все 15 единиц честно помечены `REDMINE_WRITE_FORBIDDEN`; payload'ы готовы к повторной публикации в §11 + §5/§6.

1. Выдать учётной записи Redmine, под которой работает MCP-сервер, право `Issues: add` в проекте `login` (и, желательно, право просмотра собственного профиля — судя по отказу `kind=me`).
2. Либо предоставить токен с правом записи — после этого повторить публикацию готовыми payload'ами (§11), без перепроектирования модели.
