## 3. Неоднозначности

### AMB-01 — Механизм и поведение «обязательности» полей не определены
- **Severity:** Major (Non-blocking)
- **Локация:** R-02. Цитата (строка 27): «Оба поля обязательны для заполнения (атрибут required).»
- **Суть:** Указан лишь атрибут `required`, но не определено, какая семантика авторитетна: клиентская нативная HTML5-валидация (браузер останавливает отправку), серверная проверка обязательности, или и то и другое. Отсутствует триггер и ожидаемое поведение при отправке формы с пустым полем: системная подсказка браузера, кастомное сообщение, ответ сервера — не специфицированы. Условие «обязательны» без описания реакции системы — условие без триггера.
- **Влияние на вердикт:** Сам по себе дефект не блокирует (проверка наличия атрибута в DOM решаема), но делает непроверяемым поведенческий аспект; вкладывает требование в Open Question OQ-1.
- **Вопрос (OQ-1):** Что именно проверяется при отправке формы с пустым полем — нативная подсказка браузера и блокировка отправки, либо серверная валидация с сообщением? Где и какой текст отображается?

## 4. Пробелы полноты (Gaps)

### GAP-001 — Объём легитимной части менее 3 предложений (триггер Failure Behaviour §10)
- **Severity:** Critical (**Blocking**)
- **Локация:** строки 25–27. Цитаты (единственные два предложения требования): «На странице должны быть два поля: "Email" и "Пароль".» и «Оба поля обязательны для заполнения (атрибут required).»
- **Суть:** Легитимный текст требования состоит из 2 предложений (заголовки не считаются). По правилу скилла (§10 Failure Behaviour) «issue < 3 предложений → FAIL, GAP-001». Требование описывает только статический состав формы и не покрывает назначение артефакта — процесс авторизации.
- **Вопрос (OQ-6):** Владелец требования: расширить текст до полного описания функциональности (состав формы, действия пользователя, сценарии успеха/отказа) либо явно сузить scope issue до «статический состав формы» и подтвердить это.

### GAP-002 — Отсутствие формальных AC для core-функциональности
- **Severity:** Critical (**Blocking**)
- **Локация:** raw, строка 12: «Acceptance Criteria в задаче: нет (в описании отсутствуют формальные AC в формате Given/When/Then)»; секция AC в тексте отсутствует.
- **Суть:** Ядро требования (форма авторизации) не имеет ни одного критерия приемки. По критерию вердикта (§5 шаг 4) «нет АС для core» — Blocking. Без AC нельзя формально зафиксировать «прошло/не прошло» для цели «авторизация»: ревьюер не вправе додумывать AC вместо владельца (Constraint: не переформулировать требования).
- **Вопрос (OQ-7):** Какие формальные AC (Given/When/Then) соответствуют сценариям: открытие страницы, состав полей, пустые поля, успешный вход, отказ входа?

### GAP-003 — Не определено действие отправки формы (кнопка, эндпоинт, метод, адрес страницы, сценарий успеха)
- **Severity:** Major (Non-blocking)
- **Локация:** отсутствующее требование; контекст — строки 25–27 (описан только состав полей).
- **Суть:** В требовании нет элемента отправки (кнопка «Войти» и т.п.), не указан адрес самой страницы авторизации, эндпоинт и метод запроса, не описано поведение после успешной авторизации (редирект, сессия, отображение пользователя). Функция «вход» как процесс отсутствует целиком.
- **Вопрос (OQ-2):** Каковы URL страницы, контроллер отправки, эндпоинт/метод запроса и ожидаемое поведение при успешном входе?

### GAP-004 — Не определена обработка ошибок (неверные учётные данные, ошибки сервера, сетевые сбои)
- **Severity:** Major (Non-blocking)
- **Локация:** отсутствующее требование; контекст — строки 25–27 (обработчики ответов не упомянуты).
- **Суть:** Не заданы тексты и условия появления сообщений: неверный email/пароль (401), ошибка сервера (500), иные коды (403/429/502/503), таймаут/отсутствие соединения. Невозможно спроектировать негативные сценарии.
- **Вопрос (OQ-3):** Какие сообщения и поведения UI предусмотрены для каждого класса ошибок?

### GAP-005 — Не определены типы полей и правила валидации формата
- **Severity:** Minor (Non-blocking)
- **Локация:** R-01. Цитата (строка 26): «должны быть два поля: "Email" и "Пароль"».
- **Суть:** Не указано: является ли поле Email полем `type="email"` (HTML5-валидация формата), скрыт ли ввод в поле Пароль (`type="password"`), применяются ли дополнительные проверки формата email. Трактовка влияет на тесты состава формы.
- **Вопрос (OQ-4):** Какие типы input и правила форматной валидации установлены для полей?

### GAP-006 — PRECOND_DERIVED: формальные предусловия отсутствуют
- **Severity:** Minor (Non-blocking)
- **Локация:** весь документ (секция «Предусловия» отсутствует).

Производные (DERIVED) заготовки: (1) тестовое окружение доступно; (2) страница авторизации доступна по адресу (адрес — OQ-2); (3) существуют тестовые учётные записи (зависит от OQ-2/OQ-3).
- **Вопрос (OQ-5):** Подтвердить/зафиксировать предусловия после закрытия OQ-2.

### GAP-007 — Исходный текст без нумерации требований → присвоены временные ID

## 5. Проблемы тестируемости

### TEST-01 — Критерий проверки «обязательности» полей не верифицируем поведенчески
- **Severity:** Major (Non-blocking)
- **Локация:** R-02. Цитата (строка 27): «Оба поля обязательны для заполнения (атрибут required).»
- **Суть:** Проверка наличия атрибута `required` в DOM — решаема («прошло/не прошло» определимо). Но поведенческая трактовка «обязательны для заполнения» (что произойдёт при отправке пустой формы) не имеет ожидаемого результата, а значит тест не может дать однозначный вердикт. Корень — AMB-01 (OQ-1); отдельного второго дефекта здесь нет, запись фиксирует следствииe для тестирования.
- **Вопрос:** См. OQ-1. До ответа — тестируема только атрибутивная часть (наличие `required`).

**Оценка остальных блоков:**
- R-01 (наличие двух полей «Email» и «Пароль») — формально тестируем (DOM-проверка), но затрагивается OQ-4 (типы полей) и общими блокировками GAP-001/GAP-002.
- Формальных AC нет ни одного (GAP-002) — оценивать тестируемость AC нечего.
