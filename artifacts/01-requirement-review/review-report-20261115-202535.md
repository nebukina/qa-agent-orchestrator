## 2. Противоречия

### CON-01 — Критерий остановки отправки: перечисленное условие vs нативная HTML5-валидация
- **Severity:** Major (Non-blocking)
- **Локация:** R-02/R-03. Цитаты:
  - строка 23: «Поле "Email" имеет тип email (нативная HTML5 валидация).»
  - строка 28: «Если поля не заполнены или Email не содержит "@", браузер показывает системную подсказку и ОСТАНАВЛИВАЕТ отправку запроса.»
- **Суть:** Перечисленные условия остановки (пустые поля / отсутствие «@») уже, чем объём нативной HTML5-валидации типа `email`. Для ввода, содержащего «@», но не проходящего HTML5-валидацию (напр. `user@`), два утверждения дают взаимоисключаемый ожидаемый результат: по букве шага 1 запрос должен быть отправлен, по механизму «нативной HTML5 валидации» — браузер обязан остановить отправку.
- **Влияние на вердикт:** Основной поток (AC-1..AC-3) остаётся разрешимым, поэтому Blocking не объявлен; спорная зона ограничена граничными случаями формата email.
- **Вопрос (OQ-1):** Какой критерий авторитетен — факт прохождения нативной HTML5-валидации или буквальный признак «наличия @»? Каково ожидаемое поведение для значений, содержащих «@», но невалидных по HTML5 (пример: `user@`)?

## 3. Неоднозначности

### AMB-01 — Время жизни и способ закрытия сообщений об ошибках не определены
- **Severity:** Major (Non-blocking)
- **Локация:** R-05/R-06. Цитата (строка 33): «появляется сообщение об ошибке красного цвета: "Неверный email или пароль"»; (строка 34): «появляется сообщение об ошибке: "Ошибка сервера. Попробуйте позже"».
- **Суть:** Условия появления заданы, но отсутствует триггер исчезновения: сколько времени сообщение отображается, исчезает ли при повторной отправке, закрывается ли пользователем. Термин «появляется» не определяет ни длительность, ни размещение относительно полей формы.
- **Вопрос (OQ-3):** Какова продолжительность отображения сообщений 401/500 и механизм их снятия (повторная отправка, таймаут, кнопка закрытия)?

*(Размытый термин «красного цвета» учтён отдельной записью TEST-01 в разделе тестируемости, чтобы не дублировать один дефект двумя записями.)*

## 4. Пробелы полноты (Gaps)

### GAP-001 — Не описана обработка прочих HTTP-кодов и сетевых сбоев
- **Severity:** Major (Non-blocking)
- **Локация:** R-07 (отсутствующее требование). Цитата-контекст (строки 31–34): перечислены только «HTTP 200 OK», «HTTP 401 Unauthorized», «HTTP 500 Internal Server Error».
- **Суть:** Не определено поведение UI для иных кодов (403, 429, 502/503…), а также для сетевых сбоев: таймаут, отсутствие соединения, недоступность `/api/login`.
- **Вопрос (OQ-4):** Какое поведение страницы при статусах вне списка 200/401/500 и при сетевой недоступности эндпоинта?

### GAP-002 — Нет критериев приемки для ветки HTTP 500
- **Severity:** Major (Non-blocking)
- **Локация:** R-06 vs секция AC (строки 36–39). Цитата (строка 34): «Если сервер возвращает HTTP 500 Internal Server Error, появляется сообщение об ошибке: "Ошибка сервера. Попробуйте позже"».
- **Суть:** AC покрывают успех (AC-1), 401 (AC-2) и пустое поле Email (AC-3); сценарий 500 описан в теле, но не покрыт AC.
- **Вопрос (OQ-5):** Требуется ли формальный AC для сценария 500 и какие условия в нём фиксируются?

### GAP-003 — Не определено состояние формы во время обработки запроса
- **Severity:** Minor (Non-blocking)
- **Локация:** R-08 (отсутствующее требование). Цитата-контекст (строка 29): «форма отправляет POST-запрос на эндпоинт /api/login».
- **Суть:** Не указано: блокируется ли кнопка «Войти» до получения ответа, показывается ли индикатор загрузки, защита от двойной отправки.
- **Вопрос (OQ-6):** Каково поведение кнопки/полей, пока запрос не получил ответ?

### GAP-004 — Отсутствуют NFR для страницы авторизации
- **Severity:** Minor (Non-blocking)
- **Локация:** документ целиком (NFR отсутствуют).
- **Суть:** Не заданы: защита от перебора (лимиты попыток/блокировки/троттлинг), требования к доступности (a11y), локализация интерфейса, требования к производительности ответа UI.
- **Вопрос (OQ-7):** Какие NFR применимы (лимиты неудачных попыток, a11y, i18n, время отклика)?

### GAP-005 — PRECOND_DERIVED: формальные предусловия отсутствуют
- **Severity:** Minor (Non-blocking)
- **Локация:** весь документ (секция «Предусловия» отсутствует).
- **Суть:** Предусловия выводятся косвенно из AC. Производные (DERIVED) предусловия: (1) пользователь находится на странице авторизации; (2) существует тестовый аккаунт с известным корректным email/паролем; (3) эндпоинт `/api/login` и страница `/dashboard` доступны в тестовом окружении.
- **Вопрос:** Подтвердить производные предусловия и зафиксировать их в требованиях.

### GAP-006 — Исходный текст без нумерации требований → присвоены временные ID
- **Severity:** Info (Non-blocking)
- **Локация:** строки 20–34.
- **Суть:** Требование не имеет собственных идентификаторов; для трассировки введены временные ID R-01..R-08 (см. декомпозицию). AC-1..AC-3 существовали изначально.
- **Действие:** Временные ID использовать до фиксации официальной нумерации владельцем требований.

## 5. Проблемы тестируемости

### TEST-01 — Субъективная проверка цвета сообщения (AC-2)
- **Severity:** Major (Non-blocking)
- **Локация:** AC-2 (строка 38): «Then появляется красный текст "Неверный email или пароль"»; первоисточник — строка 33: «сообщение об ошибке красного цвета».
- **Суть:** Не зафиксировано точкое значение цвета (HEX / CSS-класс / дизайн-токен). Утверждение «красный текст» не позволяет однозначно вынести «прошло/не прошло» при автоматизированной проверке; порог «красизны» субъективен.
- **Вопрос (OQ-2):** Какое конкретное значение цвета/токена соответствует «красному»? По какому признаку (computed style, класс) принимается решение о прохождении теста?

**Оценка остальных AC:**
- AC-1 — тестируем (редирект на `/dashboard` наблюдаем). Связан с OQ-1 только по граничным определениях «валидного email» (см. CON-01).
- AC-3 — тестируем полностью: случай пустого поля одинаков при обеих трактовках CON-01, открытых вопросов не имеет.
