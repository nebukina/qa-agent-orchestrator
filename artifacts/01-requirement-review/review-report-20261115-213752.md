## 3. Неоднозначности

### AMB-01 — Триггер валидации в нормативной части не определён (условие без триггера)
- **Severity:** Major (Non-blocking)
- **Локация:** R-03/R-04/R-05. Цитаты (строки 30–32): «Если длина пароля меньше 8 символов, появляется ошибка…», «…больше 64 символов, появляется ошибка…», «…от 8 до 64 символов, ошибка не появляется».
- **Суть:** Нормативные правила описывают условные переходы без указания момента срабатывания: «появляется ошибка» — когда? AC фиксируют триггер как снятие фокуса («When он убирает фокус с поля»), однако остаётся неясным, выполняется ли валидация также при наборе (live/on-input) и/или при отправке формы. Условие без триггера в теле требования.
- **Влияние на вердикт:** Поведение на blur определимо через AC → не блокирует. Но сценарии live/submit остаются без ожидания → Open Question OQ-1.
- **Вопрос (OQ-1):** Валидация выполняется только при снятии фокуса, или также при вводе и/или при отправке формы? В какие моменты ошибка появляется и исчезает?

### AMB-02 — Определение «символа» и подсчёт длины не специфицированы
- **Severity:** Major (Non-blocking)
- **Локация:** R-02. Цитата (строка 27): «Пароль должен содержать от 8 до 64 символов включительно».
- **Суть:** Не определено, что считается «символом» при подсчёте длины: учитываются ли пробелы, выполняются ли trim ведущих/конечных пробелов, как считаются многобайтовые/суррогатные символы (Unicode grapheme vs code unit). Это влияет на граничные проверки (например, строка из 8 пробелов или 8 эмодзи).
- **Влияние на вердикт:** Номинальные границы (8/64 обычных символов) покрыты AC-2/AC-3 → не блокирует. Граничные edge-случаи остаются без ожидания → OQ-2.
- **Вопрос (OQ-2):** Как считается длина: по code point/grapheme? Применяется ли trim пробелов до проверки длины?

### AMB-03 — Способ и место отображения ошибки не определены
- **Severity:** Minor (Non-blocking)
- **Локация:** R-03/R-04. Цитаты (строки 30–31): «…появляется ошибка: "…"».
- **Суть:** Указан текст сообщения, но не определено средство отображения: inline-текст под полем, всплывающая подсказка браузера, атрибуты доступности (`aria-invalid`, `role="alert"`, `aria-describedby`), визуальное состояние поля. Невозможно задать точные ассертыPresentation/a11y.
- **Влияние на вердикт:** Сам факт появления/отсутствия текста ошибки проверяем по AC → не блокирует. Детали presentation/a11y → OQ-3.
- **Вопрос (OQ-3):** Где и как отображается текст ошибки; какие ARIA-атрибуты/роли должны присутствовать?

## 4. Пробелы полноты (Gaps)

### GAP-001 — Не описано поведение для пустого поля (0 символов)

- **Локация:** отсутствующее требование; контекст — строки 27, 30 (правила оперируют длиной, случай 0 явно не выделен).
- **Суть:** Формально длина 0 попадает под R-03 («меньше 8»), но неясно, показывается ли при пустом поле «Пароль слишком короткий» или ожидается иное поведение (сообщение об обязательном поле / отсутствие ошибки до первого ввода). Сценарий пустого поля не покрыт ни одним AC.
- **Вопрос (OQ-4):** Какое поведение и сообщение ожидаются для пустого поля (0 символов) на blur?

### GAP-002 — Не описан жизненный цикл ошибки (когда ошибка исчезает)
- **Severity:** Major (Non-blocking)
- **Локация:** отсутствующее требование; контекст — строки 30–32, AC-1..AC-4 (описано только появление/отсутствие на blur).
- **Суть:** Не задано, когда снятая ошибка убирается: при повторном снятии фокуса с корректным значением, при вводе, при отправке. Невозможно спроектировать проверку сброса состояния ошибки.

- **Вопрос (OQ-6):** Подтвердить/зафиксировать URL страницы и предусловия доступа.

### GAP-004 — Исходный текст без нумерации требований → присвоены временные ID
- **Severity:** Info (Non-blocking)
- **Локация:** строки 25–32.
