# Правила взаимодействия агентов 

## Оркестратор (qa-orchestrator)
- **Роль:** Управляет общим флоу.
- **Доступные скиллы:** Оркестратор не вызывает скиллы напрямую (или вызывает только служебные). Он делегирует задачи субагентам.
- **Правило:**
    1. Передает задачу субагенту `@review` для аудита.
    2. Ждет вердикт QG1.
    3. Если QG1 пройден (PASS/CONDITIONAL) — параллельно вызывает `@task` и `@test`.

## Агент аудита (review)
- **Роль:** Анализирует требования из Confluence.
- **Разрешенный скилл:** ТОЛЬКО `requirement-review`.
- **Запрет:** Не должен использовать скиллы проектирования задач или тестов.
- **Выход:** Возвращает Оркестратору вердикт (PASS/CONDITIONAL/FAIL) и путь к `review-report-{ts}.md`.

## Агент проектирования задач (task)
- **Роль:** Создает спецификацию задач Jira.
- **Разрешенный скилл:** ТОЛЬКО `task-design`.
- **Запрет:** Не должен использовать скиллы аудита или тестирования. Если ему нужны данные из них, он должен получить их от Оркестратора.

## Агент тестирования (test)
- **Роль:** Создает тестовую модель Qase.
- **Разрешенный скилл:** ТОЛЬКО `test-design`.
- **Запрет:** Не должен использовать скиллы проектирования задач.

## Ограничения для субагентов
Даже если в вашем списке доступных инструментов (`skill tool`) отображаются другие скиллы (например, `task-design` или `test-design`), **ЗАПРЕЩЕНО** их использовать.
Используйте только тот скилл, который соответствует вашей роли (указан выше).

## Передача артефактов
- Агент `review` читает `raw-{ts}.md` и пишет `review-report-{ts}.md`.
- Агент `task` принимает на вход только `review-report-{ts}.md` и метаданные Jira.
- Агент `test` принимает на вход только `review-report-{ts}.md` и структуру Qase.

## Правила работы при вердикте CONDITIONAL
Если вердикт QG1 = CONDITIONAL (есть Non-blocking проблемы):
1. Оркестратор ОБЯЗАН передать субагентам `task` и `test` список ID проблемных требований из `review-report`.
2. Задачи и тест-кейсы проектируются **только** для тех требований, которые не имеют открытых вопросов (Open Questions).
3. Для требований с открытыми вопросами субагенты должны сформировать заглушку (GAP) со статусом `BLOCKED_BY_OPEN_QUESTION` и не придумывать им Acceptance Criteria или шаги тестирования.
